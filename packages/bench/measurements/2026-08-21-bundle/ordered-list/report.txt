OIMDB — WHAT ONE PUBLIC API COSTS AN APPLICATION THAT NEVER CALLS IT

Two applications are bundled, tree-shaken, minified and gzipped. They are the same program
except that one of them asks for an ordered list. The difference between them is what a METHOD
on OIMDB would have charged every application that never asks — because every consumer imports
OIMDB, and a bundler cannot drop a class's methods one at a time. A single bundle size settles
nothing; only the gap does.

  THIS IS THE NUMBER EIGHT SITES IN THIS REPOSITORY QUOTE AS "some 2.7 KB — around 4% of the
  package", and it is the whole quantitative half of the argument for `createOrderedCommands`
  being a free function rather than a method on `OIMDB`. Read it as the cost a METHOD would
  have imposed: every consumer imports `OIMDB`, a bundler cannot drop a class's methods one at
  a time, so under that design the arm on the left would have carried the same bytes as the
  arm on the right. WHAT THE DIFFERENCE CONTAINS: the `createOrderedCommands` module, the
  `diffOrderedList` module it pins, and the three-line call site — the call site is NOT
  subtracted, because an application that renders an ordered list writes one under either
  design, so treating this as the cost of the modules alone over-states it by a few dozen
  bytes. THE DENOMINATOR is every name the package exports with nothing droppable, which is
  the largest one available and therefore the least flattering to the percentage.

"core kept", "modules" AND "diff?" COUNT WHAT THE BUNDLER KEPT, NOT WHAT IT READ. All three come
from esbuild's own per-module byte contributions to the minified output: "modules" is how many
modules of @oimdb/core contributed more than nothing, "core kept" is what they came to together,
and "diff?" is what core/diffOrderedList.ts contributed on its own — or "no" where the bundler
dropped it. A module that was shaken out is absent, not counted at zero.

AN EARLIER VERSION OF THIS HARNESS READ THE INPUT GRAPH INSTEAD — every file esbuild opened,

The "diff?" column is the bundler's own answer to the question
packages/core/tests/what-an-import-retains.test.ts answers by reading import statements with no
toolchain at all. Two instruments, one fact. If they ever disagree, one of them is wrong and
finding out which is worth more than either number.

THE BREAKDOWN UNDER EACH ARM IS WHY THE COLUMN CAN BE TRUSTED TO DISAGREE. A count alone has one
way to be wrong and no way to show it; a list of modules with the bytes each one contributed can
be opened, added up, and checked against the source. database-only is printed in full because it
is the toll no consumer can avoid — what this engine charges an application that constructs a
database and asks for nothing else, module by module. The longer arms are cut to the largest
few, with the count and the bytes of the remainder on the line below; records.json keeps every
module of every arm.

IF THIS DIFFERENCE IS MUCH SMALLER THAN 2.7 KB

Then the figure quoted at eight sites in this repository is wrong and should be replaced by
whatever this run says, at every one of them, in one pass, naming this directory. That is the
only outcome that requires action, and it requires it whichever way the number went.

WHAT IT WOULD NOT DO IS OVERTURN THE DECISION. The argument for a free function has two halves
and only one of them is a size. The other is reachability, and it is not a matter of degree: as
a method the diff is in every consumer's bundle, as a free function it is in the bundle of
consumers who call it, and that holds at 2.7 KB, at 0.4 KB and at 40 bytes. A small number would
mean the eight sites overstated the price of a decision that was still the right shape — and it
would mean this project quoted a measurement it had never taken, which is the failure
measurements/README.md exists to name.

IT WOULD ALSO NOT BE A REASON TO PUT THE METHOD BACK. The cost of doing that is not this
difference — it is this difference multiplied by every application that will ever import OIMDB,
forever, none of which can opt out. The free function's cost is a line in an import statement,
paid once, by the caller who wanted it.
