THE INSTRUMENT, BEFORE ANY VERDICT

  The resolution control saw 1.99x for a deliberate doubling of work, so this instrument resolves a 2x.
  The scale control — the same body under two names — came out 0.7% from 1.00.
  THE RULE FOR THE WHOLE TABLE: no ratio within 0.7% of 1.00 is a reading.

  AND IT BITES HARDER HERE THAN ON A PRICE TABLE. A price of 34x survives a 6% noise floor without
  a scratch — nobody rereads a 34x because the instrument wobbles by a twentieth of it. A decision
  that wins by 4% does not survive it at all: the margin IS the instrument. Such a row is not a
  narrow win and it is not a tie either — the decision is UNSETTLED, which is a different sentence
  from "the two designs are equal". Equal is a claim about the designs; unsettled is a statement
  about this machine at this moment, and a quieter one may separate them. Those rows print no
  margin, because a margin the instrument could not resolve is what gets quoted on.

HOW TO READ A ROW HERE — THE OPPOSITE OF THE PRICE TABLE

  ratio = ours / floor, where the floor is THE DESIGN WE REJECTED. So the direction is inverted
  against every other table in this suite:

    below 1.00   the shipped design wins. The margin column says by how much: it is 1 / ratio,
                 because 0.40x is the ratio and "2.5x cheaper" is what a person means by it.
    above 1.00   THE REJECTED DESIGN WON AND THE DECISION WAS WRONG. Marked `!`, and it is a
                 finding rather than an error in the harness. Several pairs in this catalogue were
                 written by their authors EXPECTING to lose — a delivery list against a scan at
                 50% dirty, coalescing at one write per node per frame, a field filter at one in
                 four skipped — because a comparison that only ever vindicates its author is a
                 comparison nobody should believe. Those rows are the most valuable in the suite.

WHERE THE TWO SIDES ARE NOT DOING THE SAME WORK

On a price table an unequal floor flatters us and that is the whole risk: a primitive doing less
than our call makes the abstraction look cheaper than it is. HERE THE RISK IS A DIFFERENT AND WORSE
ONE. A floor that is not the rejected design faithfully built means we may have refused a design we
never actually measured — and then printed a number saying we were right to. That is the failure this
catalogue exists to prevent, and it cannot be checked from a ratio.

So it is checked from the caveats, which are printed in full under every row below. Each one names
what the rejected design would have BOUGHT — the reason somebody proposed it — before it names
anything else, and states which way each inequality pushes that row's ratio. No claim is summarised
here that a row does not make for itself.

ONE THING IS STRUCTURAL AND APPLIES WHEREVER BOTH ARMS RUN THE ENGINE: the price tables put our code
against a `Map` that nothing of ours can spoil, and that is no longer true when both sides call the
same compiled function through the same inline caches. One side's shapes then reach the other's
measurement inside one process. The rows where that applies say so, and say which way it leans.

  verdict  the shipped design wins — 25.0x cheaper
  ours     a delivery list built at the write — the frame walks only what was marked
  floor    a stamp written at the write — the frame scans every subscriber for this frame's stamp
  ONE OPERATION IS ONE FRAME: the stated number of subscribers out of the population are
  marked, spread evenly, and the frame delivers to exactly those. The list pays a flag test
  and a push per mark and walks only the marked; the scan pays one store per mark and walks
  the whole population every frame. So the answer turns on the marked fraction and THE ROWS
  CROSS OVER: read them as a table, never as one ratio. Both arms were checked to deliver to
  the same number of subscribers before the clock.

alt.memo.node-vs-recompute.dear-body.16-reads-per-write   [per read]   0.11x
  verdict  the shipped design wins — 8.88x cheaper
  ours     getValueForSlot — a held computed slot of an OIMComputedCollection over the list slot, derived once per write
  floor    body(list.rows) — the same body, called on every read, no node
  THE CASE A MEMO IS FOR: the dear body, sixteen reads between two writes — or sixteen
  consumers reading once each, which is the same axis. Ours derives once and answers fifteen
  reads from the node; the floor walks the list sixteen times. BOTH ARMS WRITE THE SAME LIST
  THROUGH `channel.write` before each run of reads, so the stamp is charged equally and only
  the reads differ. Ours asks the node, which compares its clock, walks its one source's stamp
  and runs the body once after each write; the floor calls the body on every read. Nothing is
  subscribed, so no frame runs on either side. The list does not change between writes, so the
  node's guard finds the value equal and keeps it — the cheapest outcome for ours after a
  derive. The node is a computed slot resolved before the clock, and every read goes through
  its owner's `getValueForSlot`, which pays `assertNotReleased` before the clock compare; its
  derive finds the list by the slot's key, one array index the floor's direct `list.rows` does
  not pay.

alt.frame-dedup.stamp-vs-set.fan-in-1   [per row per write]   0.22x
  verdict  the shipped design wins — 4.60x cheaper
  ours     compare the leaf's frame stamp, write it, push onto the frame array — no arrival is a repeat
  floor    add the leaf to the frame's Set, which dedups by containment — no arrival is a repeat
  THE ROW WITH NOTHING TO DEDUPLICATE, AND IT IS HERE BECAUSE IT IS THE ONE THE STAMP SHOULD
  WIN LEAST. Every leaf reads one root, so all 200 arrivals of a frame are first arrivals: our
  stamp never takes its early return and the `Set` never probes an entry it already holds.
  What is left in the difference is a field compare plus a field store plus an array push
  against one hash insert, with no repeat path exercised on either side. A reader who wants to
  know what the stamp is worth when the graph is a tree — one consumer per root, which is what
  most screens are — reads this row and not the other two. It is also the row that says
  whether the recovered figures can be quoted at all: if the stamp does not lead here, the
  mechanism is not what the quoted per-arrival numbers were describing. RESIDUALS. WHAT THE
  `Set` BUYS, and it is not nothing: dedup and containment are ONE operation, there is no
  per-leaf word to keep in step, and the invariant the stamp design holds by hand — a leaf is
  on the frame's list iff its stamp says so — cannot be broken, so that arm cannot list a leaf
  twice or lose one. The stamp buys back two things the `Set` cannot: it is a FRAME NUMBER, so
  it is stale again at the next frame with nobody clearing it, and it is also the DETACH — a
  leaf let go of between the write that listed it and the flush is unlisted by writing the
  same field, and the frame's pass reads it again before calling. A `Set` design needs a
  second mechanism for that and this arm is not charged for one. WHAT THE ENGINE DOES TODAY IS
  NEITHER ARM AS PRICED: `TOIMEffect.isRunScheduled` is a BOOLEAN, which the frame's pass
  clears as it consumes a leaf and `detach` writes false — the same compare and store, so the
  operation count here stands, and the self-staling property this arm is credited with is one
  the boolean does not have. The row is a reading of the frame-number arm and owes a run
  against the boolean [NO RUN BEHIND THIS FIGURE]. AGAINST US: our arm carries a frame number
  and pays a compare and a store the `Set` arm does not, because the stamp is doing the
  queue's dedup as well as its own. AGAINST THE `Set` ARM: its `clear()` is proportional to
  what it held where our `length = 0` is not, and both are inside the operation count here
  rather than hidden outside it. WHAT NEITHER ARM PAYS: the write that produced the arrival
  and the walk of `slot.effects` that carried it, which are `OIMChannel.write`'s and identical
  on both sides.

THE CONTROLS, IN FULL

control-resolution-2x   1.99x
  ours   two units of arithmetic per iteration
  floor  one unit of arithmetic per iteration
  NOT A PRICE — an instrument check, and it is printed first because nothing below it means
  anything until it passes. The true ratio is a little UNDER 2: both sides pay the driving
  loop once, so the exact expectation is (2u + L) / (u + L) with L the loop and u one unit,
  which at sixteen dependent steps per unit puts it around 1.9. A reading below 1.5 means this
  process could not resolve a deliberate doubling, and the runner voids the report rather than
  printing prices under it.

control-scale-same-body   1.01x
  ours   one unit of arithmetic per iteration
  floor  the same body again, over its own copy of the same state
  NOT A PRICE — the noise floor. The two sides are identical code over identical,
  separately-allocated state, so the true ratio is 1.00 exactly and every departure from it
  printed here was produced by this machine at this moment. The rule that follows is the one
  the whole table is read under: NO RATIO CLOSER TO 1.00 THAN THIS GAP IS A READING. It also
  bounds the per-row noise figure, which is the same idea measured again inside every pair —
  each pair times its floor twice, once before our side and once after, and prints how far the
  two disagreed.
