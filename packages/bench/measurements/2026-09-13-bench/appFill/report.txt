SCRIPTS — what each row means. Counts below are the default point's window
          (32); every count derived from the window scales with it, and each
          table states the step count the workers at that point actually ran.

  batch insert
    One step: every row written into an empty store in one batch, then settled. Both views go from empty to a full window, so both consumers must produce exactly one new state.
  insert into a populated store
    One step: 100 rows whose keys the store DOES NOT HOLD are written in one batch into the full population and settled ONCE. Every other write in this suite either loads an EMPTY store ("batch insert") or writes keys that are already there, so no row measured an insert into a store with ten thousand rows, fifty ordered buckets and a live subscription per visible row in it. The new rows are ranked below everything, so they arrive at the head of every group's window and both views must change. HOW MANY RENDERS ONE SETTLE PRODUCES IS THE STORE'S ANSWER, so this row is checked on the state both views are left showing. The untimed restore removes them again, so every sample inserts into the same state.
  the population keeps growing
    8 steps. Each writes a batch of BRAND-NEW keys — one row in 20 of the starting population, dealt into every one of the fifty groups and ranked below everything already stored — and settles ONCE. NOTHING IS REMOVED BETWEEN FRAMES, so batch 8 lands in a store that batches 1 to 7 already grew and the run ends with the store forty per cent larger than it began. "Insert into a populated store" writes one batch and takes it out again, so no row in this report has asked what an insert costs when an earlier insert is still there; and a store BULK-LOADED to this size is not a store GROWN to it. Each batch arrives at the head of every window, so both views must change every frame. HOW MANY RENDERS ONE SETTLE PRODUCES IS THE STORE'S ANSWER, so this row is checked on the state both views are left in and on having delivered at least once per frame. It is BOUNDED growth: eight frames says whether the eighth batch costs what the first did, and nothing about an asymptote.
  cold start to first render
    One step, and the ONLY row where constructing the store is inside the clock. It opens with NOTHING in existence — the previous store was disposed in the untimed restore — and closes when both consumers have produced their first rendered window over the whole population. Inside: building the store and its two derivations and subscribing them, writing every row, and the frame that delivers. Outside: allocating the rows (built once per process, as for "batch insert") and disposing the previous store. Read against "batch insert", which is this script with the construction removed: the gap is what building a store and its subscriptions costs, and nothing else in this report measures it.
  tear the screen down
    One step: the whole binding — the store, both derivations and every subscription standing over a full population — is DISPOSED, inside the clock. Until 2026-08-29 every teardown in this suite ran outside it. Nothing may be delivered by the teardown itself; and afterwards, UNTIMED, a page of rows is written into the torn-down binding and settled, and nothing may be delivered then either — which is what makes a `dispose` that disposed nothing a failure rather than the fastest row in the table. A store that REFUSES that write has proved the teardown more strongly still, and passes; only a delivery fails. The store does not exist when the script ends, so the population audit is skipped and the proof frame stands in its place.
  teardown lower bound
    One step: a hand-written screen — the whole population in a Map, two windows over it, one subscriber per visible row and the two view bodies — is GIVEN BACK, inside the clock, by dropping the one reference that reaches it. NO STORE AND NO LIBRARY. A LOWER BOUND on what a teardown can cost: everything the screen owns is reachable only from the screen, so no store can give one back for less than a reference store, and clearing the structures instead would be a floor any store that releases a root would beat. Afterwards, UNTIMED, a page is written into the torn-down screen and its views are called, and nothing may be delivered — which is what makes a teardown that tore nothing down a failure here.
  patch one column
    32 steps. Each patches `label` — read by the consumer, indexed by nothing — on one row visible in view A. View A must re-render with new text every step; view B, over a different group, must not change at all. How often B was WOKEN anyway is recorded.
  patch a row off screen
    32 steps. Each patches `label` on one row of view A's OWN GROUP that is ranked just below its window — watched, and not visible. Neither view may re-render: nothing on screen moved. How often each store was WOKEN for it is the whole row, and it is the cost a subscription scoped to the group pays and one scoped to the visible rows does not.
  patch an unread column
    32 steps. Each patches `note` — rendered by nothing, indexed by nothing, sorted by nothing — on one row VISIBLE in view A: the same rows, the same count and the same method shape as "patch one column", differing only in which column. Neither view may re-render. The gap between the two rows is what column-level routing is worth.
  batch patch
    One step: `label` is patched on a stride through the WHOLE population — a tenth of the rows, floored at four windows, spread evenly over every group — and the whole lot is settled ONCE. The only scenario that writes many rows inside one frame, which is what a sync response or a bulk edit is. Most of the batch lands in groups nobody watches and some of it lands in each window. HOW MANY RENDERS ONE SETTLE PRODUCES IS THE STORE'S ANSWER, not the script's: a store that holds the frame open renders once per view, one that delivers on every write renders once per VISIBLE row of the batch. Both are correct and the difference is the measurement, so this row is checked on the state both views are left showing rather than on the sequence.
  batch patch an unread column
    One step: `note` — rendered by nothing, indexed by nothing, sorted by nothing — is patched on the SAME stride through the whole population that "batch patch" writes `label` to, the same count, and the whole lot is settled ONCE. Neither view may produce new text, whatever a store does about frames: an eager store delivers per write and every one of those deliveries is redundant. The gap against "batch patch" is what a batch costs when nothing in it is displayed; the gap against "patch an unread column" is what coalescing recovers from wakeful routing. The writes are proved by the population audit, not by the digest.
  most rows change every frame
    2 steps. Each patches `label` on ONE ROW IN 2 of the whole population — half of it, the same share out of every group — and settles once. The only script that puts a store at the DENSE end of the dial: every other write row here moves a handful of a large subscribed set, which is where keeping a list of what changed beats scanning what is subscribed. Both views must end each frame showing new text. HOW MANY RENDERS ONE SETTLE PRODUCES IS THE STORE'S ANSWER, so this row is checked on the state both views are left in rather than on the sequence, and on having delivered at least once per frame.
  one frame, every kind of change
    One step: 4 rows whose keys the store does not hold are INSERTED at the head of view A's window, the 4 rows at that window's TAIL are DELETED, the rows between the movers and the sorters have their `label` PATCHED, the movers are MOVED to group B and the sorters are RE-RANKED inside the window — all before ONE settle. The five sets are disjoint by construction and `makePlan` throws if they ever meet. Every other write row in this report carries exactly one kind of change, which is the shape that hides a store keeping one maintenance path per column; a frame off a socket carries all five. Both views must end changed. HOW MANY RENDERS ONE SETTLE PRODUCES IS THE STORE'S ANSWER — a store that re-derives once per KIND delivers five times and shows one state — so this row is checked on the state both views are left in, and read against the sum of the five homogeneous rows.
  row moves between groups
    8 steps. Each moves one row from group A to group B or back. The movers are ranked below every other row, so each move is visible at the head of both windows: view A loses a row and gains the one that was just outside it, view B does the reverse.
  a row arrives mid-order
    8 steps. Each writes ONE row's `group` AND its `rank` in the same frame: out of group A into a slot INSIDE view B's window, and later back to group A at the rank it started with. Read against "row moves between groups", which moves the SAME rows between the SAME groups in the same number of steps and differs in two things: there the rank never changes, and every arrival is at POSITION 0 of the target order — the cheapest insertion a store keeping an ordered bucket can be given, chosen there to keep the move visible. Here the row arrives in the middle, so the bucket has to be searched and shifted, and the frame carries a group change and an order change at once. Both views must produce a new state on every step; HOW MANY they produce for the frame's two column writes is the STORE'S answer and not the script's — a store that holds the frame open renders once per view per step, one that flushes at the end of each write renders the intermediate state as well — so this row is checked on the state both views are left in and on a floor of one new state per view per step.
  sort key moves
    8 steps. Each moves one row's `rank` between two values that both sit inside view A's window, so the window's ROWS never change and its ORDER changes every step. View B must not change.
  the whole window re-sorted
    8 steps. Each writes `rank` on EVERY row of view A's window — 32 of them — dealing a fixed pool of ranks round the window one place further every frame, and settles ONCE. The window's ROWS cannot change (every rank in the pool sits below the lowest rank outside the window) and its ORDER changes completely every frame. Read against "sort key moves", which performs the same operation on ONE row: the pair says what an ordered index is worth as a function of how much of the order moved. View B must not change. HOW MANY RENDERS ONE SETTLE PRODUCES IS THE STORE'S ANSWER, so this row is checked on the state view A is left in and on having delivered at least once per frame.
  a consumer per group
    50 steps — ONE PER GROUP, with a consumer subscribed to EVERY group at once instead of the two every other row here uses. Each step moves one row's `rank` between two values that both sit inside THAT group's own window, so that group's order changes, its rows do not, and nothing any of the other 49 consumers shows can have moved. Exactly one consumer may produce a new state per step. HOW MANY CONSUMERS WERE WOKEN ANYWAY IS THE ROW: perfect selectivity is 50 deliveries for 50 steps, one global change signal is 50 × 50, and the counters column carries both. Each consumer renders a window, so a store with no per-group signal also pays the consumer fifty times per step.
  targeted column delivery
    16 steps in two halves. 8 rows are PINNED — resolved once before the clock and thereafter addressed by POSITION, not by key — and both consumers are re-pointed off the window views onto them: A is driven by and renders `label`, B is driven by and renders `note`, same rows, same count, same lines. The first half writes each pinned `label`, settling each; the second writes each pinned `note` the same way. Every correct store produces exactly one distinct render per pinned row in EACH half, so the answer is entirely in the DELIVERY and REDUNDANCY counters: a store that routes by column wakes one view per write, one whose granularity is the row wakes both and shows text it already had, one with no granularity re-reads everything. The rows are off screen, so no window derivation is involved. It does NOT price the pin: both halves write through it.
  cell lower bound
    16 steps in two halves, mirroring "targeted column delivery" with the store taken out. Each step writes one line of a 8-line cell view and delivers that view — the label view in the first half, the note view in the second — straight from an array of strings, through the same `deliverCells` every adapter must reach a cell view through. A LOWER BOUND: a store that routes by column delivers one of these a step and one that does not delivers two, so neither can come out below it.
  delete the visible window
    One step: every row view A is showing — 32 of them, the lowest-ranked of group A — is removed in one batch. View A must produce exactly one new state, refilled from the rows that were just outside the window; view B, over a different group, must not change at all.
  the group empties under the view
    Two steps. The first removes EVERY row of group A — not a window of it, all of it — and settles, so view A is left with nothing to show and its window cannot refill; the second writes the identical rows back as keys the store no longer holds and settles, so the whole derivation is built again. View B, over another group, must not change at all. "Delete the visible window" removes one window from a group holding two and the window refills from behind it, so no store in this report has ever been asked for an EMPTY selection, for a window larger than its group, or for a bucket to be given back and rebuilt. HOW MANY RENDERS EACH HALF PRODUCES IS THE STORE'S ANSWER, so the row is checked on the state view A is left in and on its having changed at least twice — full, empty, full.
  re-send unchanged list
    One step: the 32 rows view A is showing are written again with the values they already hold, from a freshly allocated array of freshly allocated objects. PAGE-SIZED, because that is the size a re-send arrives at — a page refetched or replayed — and a full-population re-write measured the population rather than the library. No adapter pre-filters this write — a value check has to come from the library, not from the adapter — so the row measures what each library can tell on its own. No consumer may produce new text. How many times each was woken for nothing is recorded.
  consumer lower bound
    32 deliveries of a 32-row window through `deliver` itself, alternating TWO prepared windows so every delivery is distinct, driven straight from arrays of PLAIN objects with no store underneath. A LOWER BOUND on what one delivery costs, not a constant to subtract: this script drives ONE consumer per step where most scripts have two views and the per-group script has fifty. On the SHAPE the three property loads per row are paid over: sixteen of the seventeen adapters were audited and hand `deliver` plain objects — tinybase's pool holder is an adapter-owned five-field literal, tanstack-db's row is a spread, and the signal adapters read `.value` inside the derivation and deliver the row the signal holds. MOBX IS THE ONE EXCEPTION: its window computed is over row proxies, so its loads are trapped gets and its true multiple is lower than the one printed.
  mount lower bound
    8 cycles of: mount 256 subscribers on ONE plain object, write it, run every standing body, deliver one line, unmount them all, write it again, and deliver nothing. NO STORE AND NO LIBRARY: an array of closures, a recorded position per subscriber, and an O(1) swap-remove to leave. A LOWER BOUND on what one mount and one unmount can cost — not the hand-written anchor, which keeps a store and unmounts with `indexOf` plus `splice`, and which has its own row in every churn table. The nine churn tables are scaled by this. The subscriber count is the LARGEST in the family, so this step's share of the two writes and the one delivery is the smallest any churn step's is.
  mount and unmount one subscriber
    8 cycles of: subscribe ONE consumer to ONE row, write that row, settle, unsubscribe, write it again, settle. THE FLOOR OF THE OPERATION — a single subscription over a single source, with nothing else mounted anywhere, which is what every other churn row here is read against. The mounted frame must deliver exactly once and the unmounted frame must not deliver at all.
  N subscribers on one root, oldest out first
    8 cycles of: mount 32 subscribers on the SAME row, write it, settle, unmount them FIRST-MOUNTED-FIRST, write it again, settle. What a list of components bound to one store object costs to build and to tear down. Read against "mount and unmount one subscriber" for the per-subscriber cost, and against the deep variant for whether that cost is constant in how many are already on the root.
  N subscribers on one root, newest out first
    The same script as "N subscribers on one root, oldest out first" — same 32 subscribers, same root, same frames — unmounted LAST-MOUNTED-FIRST and differing in nothing else. The gap between the two rows is what the ORDER of an unmount is worth: where a subscriber list is an array, leaving it from the front is a short scan and a long shift, and leaving it from the back is a long scan and no shift.
  N×8 subscribers on one root, oldest out first
    The same script at 256 subscribers instead of 32 — eight times as many on the one root, unmounted first-mounted-first. THE PAIR IS THE MEASUREMENT: a linear mount and a linear unmount cost eight times more per cycle here, and a quadratic unmount costs sixty-four times more. One size cannot tell those apart, which is why there are two.
  N×8 subscribers on one root, newest out first
    256 subscribers on one root, unmounted LAST-MOUNTED-FIRST. The fourth corner of the size × order square, and the one that says whether an order effect grows with the population or is a constant.
  one subscriber over many sources
    8 cycles of: mount ONE subscriber reading 64 rows at once, write the first of them, settle, unmount it, write again, settle. The other axis: the shared-root rows vary how many SUBSCRIBERS a source has, and this varies how many SOURCES a subscriber has. It is where a subscription pays for its source list — deduplicating it, expanding it, and registering in each source on the way in, then leaving each of them on the way out. Read against "mount and unmount one subscriber", whose subscriber reads one.
  N subscribers on one column
    8 cycles of: mount 32 subscribers on ONE COLUMN — `label` — of one row, write that column, settle, unmount them oldest-first, write again, settle. THE SAME SUBSCRIBER COUNT, THE SAME ROOT ROW AND THE SAME ORDER AS "N subscribers on one root, oldest out first", differing in what is subscribed TO and in nothing else — so the gap between the two rows is what addressing a column rather than a whole row costs to mount and to let go. A library with no column identity of its own has no row here — it declines `churn.column` by name and keeps the three shapes it can express — because implementing this as a row subscription under another name would print the neighbouring row's number twice.
  N subscribers over a derivation chain
    8 cycles of: mount 32 subscribers, each BUILDING ITS OWN chain of 4 derivations over 8 rows, write the first of those rows, settle, unmount them oldest-first, write again, settle. The chain is built by the mount because a component's selectors are. What it prices is the part a flat root list cannot have: reaching the roots underneath a stack of derived values, and taking the stack apart again. Read against "N subscribers on one root", which mounts the same number of subscribers over the same rows with no derivation between them.
  a write through standing chains
    8 steps, with 32 subscribers ALREADY MOUNTED — each over its own chain of 4 derivations over 8 rows, built once before the clock and standing for the whole run. Each step writes `label` on the FIRST of those roots and settles, and the delivery carries how many subscriber bodies ran and what the first of them read at the bottom of its stack. Nothing is mounted or unmounted inside the clock. "N subscribers over a derivation chain" counts MOUNTS as its steps and folds eight frames of propagation into a number about construction; this counts the frames and nothing else, so the pair separates what a chain costs to BUILD from what it costs to RUN. It is also the one chain row where both sides do the same job — the mount is what the two cannot be compared on, and there is no mount here.
  churn against a standing population
    256 subscribers are mounted on one row BEFORE THE CLOCK and stay for the whole sample; then 8 cycles of: mount 32 more on the same row, write it, settle, unmount those, write it again, settle. THE QUADRATIC ASKED THE WAY AN APPLICATION ASKS IT — a screen does not build and destroy its whole subscription set, it keeps most of it and churns a fraction. If mount and unmount are O(1) in what is already standing, a pair here costs what a pair costs in "N subscribers on one root"; if either is linear in it, the resident set is what this row is paying for. BOTH frames of a cycle deliver here, and the second one naming the resident count rather than the full one is the proof that the churned subscribers left.
  the application mounts
    One frame. THE SCENE IS 80 CARDS IN 10 DECKS OF 8, WITH 5 USERS, and 300 subscribers are mounted over an already-loaded store — one per card (80), one per deck's name and one per deck's date (10 each), and one per MOUNTED TAG (200, because a card starts with 1 to 4 of them) — then every one of the application's 95 rows is written once and the frame is settled. The delivered line names how many bodies ran, which must be exactly the number mounted: this family has no other witness that a subscription exists, and a mount that wired nothing leaves the same population behind as one that wired everything. WHAT IT IS READ AGAINST: `mount and unmount one subscriber` and `N subscribers on one root` price a mount with nothing else happening and every subscriber on ONE row; this is the same act at an application's scale and shape — 300 subscribers spread over 95 rows, with 210 of them sharing the 5 user rows. THE TEARDOWN IS NOT IN THE CLOCK: the subscribers are let go in the untimed restore, because what an application costs to take down is `give the screen back`'s question.
  one application update round
    20 rounds, over an application mounted before the clock. ONE ROUND: every card's tag list advances 1→2→3→4→1 — 60 cards gain a tag and the other 20 lose three, so 60 subscribers are mounted and 60 let go — then every deck is renamed (10 writes), every card's `open` is toggled (80 writes), the round's user advances its setting (1 write), and the frame settles. 132 bodies run in it: every deck name, every card, and the 40 tags and 2 deck dates of the one user that moved. DATA AND SUBSCRIBERS MOVE IN THE SAME FRAME, which nothing else in this report does: the churn rows mount and unmount over a population that never changes, and the write rows move data under a subscriber set that never changes. Read against `the application mounts` for what the same subscriptions cost when they are all built at once, and against `a shared setting moves` for the round with the cards' half taken out. The run is a whole period of the scene — a tag list returns every 4 rounds and the user rotation every 5 — so it ends with exactly the subscribers it started with.
  a shared setting moves
    20 steps, over an application mounted before the clock. EACH STEP is ONE WRITE — a user's clip setting — and a settle. Nothing is mounted, nothing is unmounted, no card is written. 42 bodies run per step: the 40 tags whose text is that user's setting applied to a label, in 40 DIFFERENT cards, and the 2 decks that user authored, which read the same number as a date precision. The steps rotate through the five users, so a run moves every setting four times and reaches every tag in the application. WHAT IT MEASURES is routing and nothing else: one write, one frame, and the question is how much of the application a store has to walk to find the fifth of it that reads that row. Read against `one application update round`, which is this plus every card and every deck written and the tag lists moved — so the gap between them is what the cards cost — and against `N subscribers on one root`, whose subscribers all read ONE row and none of the others. SUBSCRIBER 0 IS A CARD AND DOES NOT READ ANY SETTING, so a correct store renders ONE distinct state across the whole run and the other 19 deliveries are redundant by construction: what separates the participants here is how many bodies each ran, which the line carries, and how much it cost to find them. WHAT THIS ROW MAY NOT BE QUOTED FOR: a step is a FIFTH of the application and not all of it. There are 5 users and a tag belongs to ONE of them, so a setting is read by 42 of the 300 subscribers standing — a run reaches every one of them by rotating, a single step does not. A source read by all eighty cards at once would be a different scene, and inventing one would make this row incomparable with the exodra suite's rows over the same application.
  read a page by key
    8 steps. Each asks the store for 32 rows BY KEY — a disjoint page of a stride through the whole population — and renders `id rank label` for each, all three columns read out of the store. THE ONLY TIMED READ IN THIS SUITE, and the only script whose delivery is a PULL rather than a change signal: nothing is written and nothing settles. No adapter may resolve these keys in advance — the lookup is what the row measures, which is the exact opposite of what "targeted column delivery" pins away. The hand-written floor answers the same page with one map read per key.
  scroll the window
    8 steps. Each moves view A's OFFSET into group A — out to a full window in four strides and back to zero — and settles. NOTHING IS WRITTEN: no rank moves, no row changes group, and the order of the group at the end is the order it had at the start, which the population audit confirms. Every step must produce a new window; view B, the two-axis window over the same group at a fixed offset, must not change at all. Read against "the whole window re-sorted", which re-points the same per-row subscriptions for the opposite reason — there the data moved under a fixed window, here the window moved over fixed data.
  a view filtered on two axes
    4 steps, with TWO views over the SAME group: view A selects on `group` alone and view B on `group` AND a second axis derived from the key. Step 1 moves a row that is ON the second axis out of group A, step 2 moves one that is NOT, and steps 3 and 4 bring them back. View A must produce a new state on all four; view B on exactly two, because the other two concern a row its second predicate had already excluded. HOW OFTEN VIEW B WAS WOKEN ANYWAY IS THE ROW. It does NOT measure a move of the second axis itself: that axis is derived from the key and nothing can write it — see the scenario comment for why the dataset has no sixth column.
  relation lower bound
    16 steps in two halves, mirroring the two relation scripts with the store taken out. The first half writes a name into the 8-line joined view and delivers it, once per step; the second does the same for the pair view. Straight from arrays of strings, through the same `deliverRelation` every adapter must reach a relation view through. THE JOIN IS NOT IN IT: the owner and the pair record are resolved once in `holdRelation`, outside the clock, so a delivery reads a field per line. This is what every participant pays alike, and neither relation script can come out below it.
  a write to a related entity
    8 steps over TWO ENTITY TYPES. 8 rows point at 4 owners, two rows each. Each step writes ONE OWNER'S `name` — a record of the SECOND type — and settles; no row is written at all. View A renders one line per row carrying THAT ROW'S OWNER'S NAME, so every step must produce a new state there and each one moves two of the lines. View B, over the same rows through their pair records, must not change at all — a delivery there is a store that cannot tell a write to an owner from a write to something keyed by that owner. THE RELATIONSHIP IS IMMUTABLE: nothing here re-parents a row, and the scenario says so against A1.
  a record keyed by two identities
    8 steps. Each addresses the record for ONE (owner, row) PAIR — a key COMPOSED per call out of two identities the binding already holds, never cached — and writes its `mark`, then settles. View B renders those marks and must produce a new state every step; view A, the joined view over the same rows, must not change at all. THE COMPOSITION IS THE MEASUREMENT: an engine whose composite key is a chain of identities descends a tree, a hand-written store joins two ids into a string and probes a map, and both build exactly one address per call. The records exist before the clock, so no step is a mint. WHICH OF THE TWO A ROW BUILDS IS A FACT ABOUT THAT ROW: `oimdb-3.12.1` keys these records by a tuple of two SCALARS, `oimdb` by a chain of two collection SLOTS, so both shapes of composite key are in this table. What is not here is the current engine against ITSELF: it ships a scalar arm (`OIMSlotByKeyStoreScalarTreeDriven`) that no adapter in this suite constructs.
  single-value lower bound
    32 deliveries of ONE formatted line through `deliverSingle` itself, each carrying a different prepared value so every delivery is distinct, with no store underneath and no value held anywhere. The two single-value tables are scaled by this. A correct store delivers exactly one of these per write, so this bound is TIGHT and not merely a floor — the gap between a row here and 1.00 is that row's store and nothing else.
  write one value
    32 steps. Each writes a NEW value to a single value the library holds — no key, no collection, no window, no grouping, no rows anywhere in the path — and settles. View A is driven by and renders that value and must produce new text every step. A SECOND value stands beside it with its own subscriber and is never written; view B must not change at all, and how often it was WOKEN anyway is recorded. The address is resolved once before the clock, so no lookup is charged to any row here.
  re-write one value
    32 steps. Each writes the single value THE VALUE IT ALREADY HOLDS, and settles. No adapter pre-filters it — a value check has to come from the library, not from the adapter — so the row measures what each library can tell on its own. NO CONSUMER MAY PRODUCE NEW TEXT, in either view. How many times each was woken for nothing is recorded, and that count is the answer: a library that compares before it notifies delivers nothing, one that does not delivers 32 times and shows the same line every time.

   WHERE THE RECORD ITSELF IS WEAK — an item is not the same thing as its check:

     C1   THE LOAD GATE CANNOT POLICE ITS OWN THRESHOLD. The allowance subtracts one runnable process
          per worker — each worker's MAIN thread — while V8 also marks and sweeps on helper threads,
          so a heavy adapter holds the average up on its own and the surplus is counted as somebody
          else's. `loadavg()` cannot say whose work it is, and the per-worker weight that would make
          the subtraction exact is not a constant. The error refuses pieces that would have been fine
          rather than admitting bad ones; what a reader takes on trust is that no piece was admitted
          that should not have been, which this gate cannot demonstrate. See `load.ts`, and the spread
          of foreign readings the runner derives from the pieces it found.

     C1   THE PIECES ON DISK DISAGREE ABOUT WHAT THEY SUBTRACTED. `selfAllowance` is younger than the
          results directory: pieces written before 2026-09-01 allowed themselves one worker and
          recorded nothing, and the rest record the count they allowed. Absent is NOT the same
          statement as 1.00 — it is "this piece cannot say" — so a combined table spans two
          subtraction rules judged against one gate. Every printer passes `foreignPeak` through
          `ownAllowanceText` rather than assuming, and the counts are derived beside the pieces.

     C6   NO TIMING RUN OF THE CURRENT ENGINE HAS BEEN RECORDED. `measurements/` is the only directory
          a published figure may name, and no directory in it was written by this harness — so nothing
          under it speaks for the engine as it stands, and C6 is unmet by every timing figure rather
          than by some of them. `results/` holds the pieces the report is rebuilt from; a piece is an
          intermediate and not a citation.

     B1   THE INDEX IS PRICED IN TWO FAMILIES AND NOT IN FIVE. B1 asks that an asymmetry be printed on
          the row it affects, and the asymmetry this report can price is the group index:
          `baseline-array-indexed` against `baseline-array`, the same scripts at the same point. That
          anchor declines the churn, relation and single wirings, so those tables carry ONE
          hand-written row and the gap is not printed above them. B2 has a subject there; B1 has no
          priced asymmetry.

   B1 and B2 turn on what the hand-written floor IS. That was an open decision until 2026-08-29
   and is now settled by shipping BOTH arms: `baseline-array`, which keeps no group index, and
   `baseline-indexed`, which keeps one and differs in nothing else. The gap between them is the
   price of the index, printed under every table.

   THE MEMORY PASS — not a scenario, and it signs too. 10 of 15 NOT MET: A1, A2, A3, A4, B4, C2, C3, C5, B5, C6.

   It runs no script: it loads the population and reports what the store holds, so several of the
   items name a clock it does not start, and the three artifact-time checks above —
   firstFoldedRedundancy, firstEstimatorMismatch, undrivenRowsOf — have nothing to read on a
   weighed row. Where an item's subject is absent it is NOT MET saying so, never MET on the
   grounds that a demand nobody can fail is satisfied; where the subject IS present the answer is
   MET on the same rule the load-time checks apply to a script. B5 and C6 are derived here from
   ADAPTERS, from the piece, and from what is on disk, as they are for every script above.

     · A1   NOT MET — this pass times nothing, so the item's subject is absent rather than satisfied.
            What stands where a clock would be is a check: after the load, `worker.ts` requires exactly
            one distinct render from each of the two consumers and a full window in view A, reads them
            BEFORE the binding is given back, and reports `failed` rather than a figure when either is
            wrong — so a store that quietly held nothing cannot post the smallest number in the table.
            That refuses an empty store; it does not put a consumer at the end of a timed operation,
            because there is no timed operation for it to end. `undrivenRowsOf`, which asks this per row
            of a stored piece, has no counters to read on a weighed row.

     · A2   NOT MET — no delivery counter travels with the figure. The `weighed` arm of `TWorkerResult`
            carries `baseline` and `held` and nothing else; the consumers' `deliveries`, `distinct` and
            `redundant` exist in the worker, are read once for the load check, and die with the process.
            So `firstFoldedRedundancy` — the arithmetic that holds the SUITE to A2 on every timing row,
            `deliveries === distinct + redundant` — has nothing to run over here. A store that woke its
            two views fifty times to reach the state one wake would have reached weighs exactly the same
            in this table, and nothing in the piece could show it.

     · A3   NOT MET — `BenchOracle` is never constructed in this mode, and could not answer if it were:
            the reference model is a plain-Map derivation whose product is the RENDERED STATES, and it
            holds no opinion about how many bytes a store should occupy. There is no independent model
            of a heap here and no second implementation to disagree with the first. The stored state is
            checked for EXISTENCE — one distinct render per view, a full window in A — and not walked
            row by row against a model, because the mode runs no script for a model to replay.

     · A4   NOT MET — the item pairs two things and this pass produces only one of them. A4 is met
            elsewhere BY CONSTRUCTION — `worker.ts` emits `status: "ok"` only downstream of
            `proveThisPass`, so a timing process cannot publish a number it did not also verify — and
            this mode reaches its `weighed` emit by another path entirely. The half that exists is in
            the right place: the load check runs in the same process, on the same binding, between the
            two heap readings, and the binding is disposed only after the second one, so nothing it
            holds can have been collected before it was weighed. But there is no timing to be separate
            from, and a MET would be claiming a property of a number this pass does not produce.

     ✓ B1   MET — wrong if — an adapter weighed under a wiring or a population other than the one every
            other row gets, or this table falling to a single row. The mode calls `adapter.bind`,
            `binding.write(loadRows)` and `binding.settle()` and nothing else, so a per-adapter shortcut
            in any of the three would make this column two different jobs; and a comparison needs two
            sides, which is the same condition `assertAgreesWithTheCode` throws on for a script — here
            it is derived rather than thrown, because how many rows this table has is a fact about the
            piece and B5 reports it. The asymmetry that does exist prints under the table: the id →
            signal map preact-signals and alien-signals keep, and jotai's ids atom, named there as
            bookkeeping the library does not do for itself.

     ✓ B2   MET — wrong if — either anchor ceasing to be weighed here. B2's subject in this report is
            the ANCHOR PAIR — `baseline-array`, which keeps no group index, and
            `baseline-array-indexed`, which keeps one and differs in nothing else — and this pass weighs
            BOTH as full rows, under the same `bind` and the same population as every library beside
            them, which is the strongest position any table in this report holds on B2: the write and
            read tables have both anchors, the churn, relation and single tables have one. So the bytes
            a group index costs are readable directly off two rows of this table. What is NOT claimed
            here is that anything is DIVIDED by them — that is B4, and it is NOT MET.

     ✓ B3   MET — wrong if — an adapter whose `bind` held values its library does not hold, with nothing
            under this table naming it. This is the column where that departure is least escapable and
            most invisible: bookkeeping a library forces on its user costs no milliseconds in a table
            that pays for it and costs bytes here. A row whose `admission` line stopped describing where
            its values live would put those bytes in the column with no way for a reader to attribute
            them.

     · B4   NOT MET — no floor takes the consumer's share of this figure, and `floorKeyFor` has nothing
            to hand a table that is not a scenario — which is the same condition it throws on for a
            script declaring B4 MET. The consumers themselves are outside the delta: `makeConsumers` and
            `makeGroupConsumers` run at module scope, before this mode's first collection, so the
            preallocated line buffers — the two-view set and the fifty-view set alike — are in every
            adapter's baseline and in no adapter's delta, and the worker says so. What is NOT outside it
            is the load's own render: `BenchConsumer.row` builds a formatted string per visible row and
            stores it in the buffer, so one window of freshly allocated lines per view is still
            reachable when the second reading is taken and is inside `held` for every row. Every adapter
            renders the same window of the same text — that is what the digest comparison establishes in
            the verify pass, which this mode does not run — so it is a constant of the column rather
            than a difference between rows. Nothing measures it, and there is nothing to subtract it
            from.

     ✓ C1   MET — wrong if — the memory piece printing its conditions line only when something was
            wrong, or judging "busy" against the gate it was permitted rather than against the default
            one. Like every other piece it goes through `run.load.refusal()` before a single worker is
            spawned, stores `load.summary()` in the piece it writes, and prints through
            `busyForTheDefaultGate`. This is MET only in the sense C1 is met anywhere in this report —
            that the conditions were RECORDED — and it inherits the first two entries of `STANDARD_GAPS`
            whole, since the gate cannot police its own threshold for a memory worker either.

     · C2   NOT MET — every row of this column is ONE reading from ONE process, and a single observation
            is not an estimator. The rule is uniform and the table states it, so the column does not MIX
            — and `firstEstimatorMismatch`, which holds a timing column to one stored plan, has no plan
            and no per-row `repeat` or `samples` to read here. "The minimum of `samples` runs, and the
            minimum over `processes`", which is the estimator every other column in this report is read
            under, is not in force and must not be: the smallest of several heaps is the luckiest
            collection rather than the smallest store. The item has no answer for a column that
            estimates nothing, and a MET would import a sentence a reader would then apply to these
            numbers.

     · C3   NOT MET — nothing measures the variation. One process and one reading per row, so there is
            no spread and no drift beside these numbers; `SPREAD_CEILING` is met elsewhere by
            construction — `run.ts` refuses a place to every row over it, on one code path — and this
            table awards no places for it to refuse. What prints instead is a BOUND and not a
            dispersion: V8 compiles each library's write path between the two readings and compiled code
            counts in `heapUsed`, so the table says two rows that close together have not been told
            apart. A second process would produce a different figure and this table would not know by
            how much.

     ✓ C4   MET — wrong if — two adapters weighed inside one process. C4 is taken on trust everywhere in
            this report and enforced upstream — a worker is spawned with ONE adapter name — and here
            that spawn is visible in the loop itself: every row is its own `runWorker(name, NO_SCENARIO,
            "memory", …)`, and therefore a fresh V8 with exactly one library's write path compiled in
            it. Folding that loop into a single process would both teach one call site two shapes and
            weigh a heap that already holds somebody else's store.

     · C5   NOT MET — no control is weighed beside these rows. C5 is answered for a script by asking
            whether every arm of `CONTROLS` supplies its wiring; the controls are bodies over a store
            driven by a SCRIPT, and this pass runs none, so there is no wiring for them to supply and
            the question has no form here. What the table prints in place of an attestation is an
            argument — compiled code counts in `heapUsed`, so two rows that close together have not been
            told apart — and an argument is a bound on the instrument, not a reading of it. The missing
            instrument exists one directory away: `retained/retainedControls.ts` weighs a KNOWN number
            of references at two sizes and voids its report unless both land on the same platform
            constant, and `control-noise.identical-populations` is its byte floor. It cannot be lifted
            across unaltered. `npm run retained` compares two bodies in ONE process, built to be as
            alike as they can be made, which is what lets an absolute reading's error cancel between
            them; a row per library, each in a process of its own, has no such premise, and a byte floor
            measured between two IDENTICAL populations is not a floor between two different ones.
            Nothing in this pass has been attested at the scale of a `held` figure.

     · B5   NOT MET — nothing was weighed: 17 libraries were asked and none produced a figure. A table
            with no rows covers no field, and B1 above has no second side to be about.

     · C6   NOT MET — no usable memory piece — stale (measured 2026-09-12T20:19:03.485Z) — harness
            sources; subject sources (core / core-legacy). Any figure quoted for what a store holds
            would name no artifact that can be re-derived or refuted.

════════════════════════════════════════════════════════════════════════════════════

   A row is given #k only where it held place k at EVERY point — and a place at a point is only
   given to a row this machine told apart from every row above it there (same rule, same drift,
   same helper as the tables above).

   Everything else carries ≈ and the range of places it occupied: lowest place any point left
   open to it, highest place any point put it at. Read ≈ #2-#6 as "somewhere in that band, and
   which dial you turn decides where".

   Cells are per point: #k where that point gave a place, lo-hi where it did not (the row
   overlapped something above it), — where the row was not measured there at all. NO TIMES ARE
   REPRINTED HERE: each point has its own sampling plan, its own resolution control and its own
   drift, so its milliseconds stay in its own table.

   THIS IS THE ONE BLOCK THAT READS ACROSS PIECES, and therefore the one place where WHEN each
   piece was measured matters. Every cell comes from its own piece, measured in its own sitting;
   the PIECES block above gives the span and the load of each. What is compared here is a PLACE —
   never a duration — and a place was established inside one piece against that piece's own drift,
   so nothing here rests on two pieces having been measured under the same conditions. What it
   does rest on is their being the same EXPERIMENT, which is why a piece whose sources, lockfile,
   Node or machine differ is refused above rather than ranked here.
